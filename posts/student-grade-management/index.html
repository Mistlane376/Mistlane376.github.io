项目实践：学生成绩管理系统

发表于2026-06-19|更新于2026-06-19|项目练习
|总字数:4.8k|阅读时长:20分钟

一、项目背景

作为一名计科专业的学生，这学期《面向对象程序设计(Java)》的课程设计给了我一个将理论知识付诸实践的机会。我选择开发一个基于 Web 的课堂点名系统，主要解决传统课堂点名中存在的两个痛点：

  • 随机点名不公：纯随机点名可能导致某些学生被频繁点到而另一些学生长期被忽略
  • 数据难以沉淀：点名结果缺乏系统化记录和统计分析，教师无法回溯历史点名情况

经过几周的努力，我完成了这个名为 AttendanceSystem 的项目。它不仅仅是一个点名工具，更是一个完整的学生管理与数据统计平台。

二、技术选型

在技术栈的选择上，我采用了经典的 Java Web 组合：

层次 技术
后端核心 Java Servlet + JSP
数据库 MySQL 8.0
数据库连接 JDBC + 自封装 JDBCUtil
Excel 处理 Apache POI 5.2.5
JSON 序列化 Jackson 2.15.2
数据可视化 ECharts 5.5.0
前端交互 原生 JavaScript + Fetch API
服务器 Apache Tomcat 9.0

整套系统采用 MVC 分层架构，分为控制层（Servlet 接收请求分发）、服务层（Service 处理业务逻辑）、数据访问层（DAO 封装 SQL）和模型层（Model 数据实体），各层职责清晰。

五、★ 开发中遇到的三个核心困难

困难一：外键约束导致删除失败

问题：最初删除学生时，attendance_record 表的 FOREIGN KEY 约束阻止了删除操作，因为该学生有历史点名记录。

解决：在 DAO 的 deleteStudent() 方法中，使用 SET FOREIGN_KEY_CHECKS = 0 临时关闭外键约束，先删除关联记录，再删除学生，最后恢复约束：

收获：异常处理中必须考虑恢复现场——无论是否发生异常，SET FOREIGN_KEY_CHECKS = 1 必须在 finally 中再次执行，否则整个数据库会话的外键检查都被永久关闭。

困难二：双表操作的事务一致性

问题：点名时需要同时执行两个 SQL——更新 student 表的统计字段和向 attendance_record 表插入记录。最初两个操作各自从 JDBCUtil.getConnection() 获取独立连接，导致一个成功一个失败时数据不一致（学生统计更新了但记录没写入）。

解决：在 CallService 层统一获取一个 Connection 对象，关闭自动提交，将同一个连接作为参数传入两个 DAO 方法，最后统一 commit 或 rollback：

收获：良好的分层设计需要为事务场景预留灵活性。DAO 方法应当提供接受外部 Connection 参数的重载版本，让 Service 层有能力控制事务边界。

困难三：JSP 模板字符串与 EL 表达式冲突

问题：前端 JavaScript 中使用了 ES6 的模板字符串语法 `${变量名}`，与 JSP 的 EL 表达式（${...}）语法完全一致。Tomcat 的 JSP 编译器在编译 .jsp 文件时，将 <script> 标签内的 ${...} 当作 JSP 表达式处理，导致 ClassNotFoundException 和 500 Internal Server Error。

错误日志：

解决：将所有 JavaScript 模板字符串改为传统字符串拼接（+ 连接），同时将箭头函数 => 改为 function，let/const 改为 var，确保最大兼容性：

收获：JSP 虽然是 Java Web 开发的经典技术，但在与现代 JavaScript 混用时存在语法冲突。后续可以考虑前后端分离（如 Vue.js + REST API）彻底避免这类问题。

困难四：文件上传时 FormData 导致 request.getParameter() 获取不到参数

问题：编辑/删除学生时，前端使用 FormData 封装参数并通过 fetch POST。但后端 request.getParameter("action") 始终返回 null，导致操作始终返回「未知操作」。

原因：FormData 默认使用 multipart/form-data 编码，Servlet 容器需要 @MultipartConfig 注解才会解析 multipart 请求体中的参数。

六、★ 项目亮点

6.1 公平调度点名算法

不是简单的 Math.random()，而是基于「最少被点名优先」原则的加权随机。同时加入连续答错保底机制，避免了「差生永远答不出」的尴尬循环。

6.2 数据库冗余字段设计

student 表的 total_called 和 total_correct 是统计冗余字段。每次点名时用 UPDATE ... SET total_called = total_called + 1 原子更新，避免了 SELECT COUNT(*) FROM attendance_record GROUP BY student_id 的昂贵查询。

6.3 纯前端实时搜索

一行 tr.textContent.indexOf(q) 完成多列匹配，过滤延迟为零。

6.4 批量导入三级校验

文件导入时经历了「前端去重 → 数据库查重 → SQL 异常兜底」三级防护，确保脏数据不进库。

6.5 CSV 导出 BOM 兼容

导出 CSV 时在文件头写入 UTF-8 BOM (﻿)，确保用 Excel 打开时中文不乱码。

七、不足与改进方向

  1. 密码明文存储：当前 sys_user 表密码为明文，应当改为 BCrypt 哈希存储
  2. 点名算法维度单一：目前只在全局范围内按次数分派，后续可以增加按班级维度点名的模式
  3. 缺少单元测试：重构时容易引入回归 bug，应补充 JUnit + Mockito 测试
  4. 前端代码冗余：原生 JavaScript 操作 DOM 代码量大，后续可引入 Vue.js 简化数据绑定
  5. 数据库连接：目前使用 DriverManager 每次获取新连接，生产环境应改用 Druid/HikariCP 连接池
  6. 无权限控制：目前只有 role 字段但未实际使用，应区分管理员/教师权限

八、课程设计感想

这次课程设计让我完整经历了一个 Java Web 项目从零到一的开发过程。

最大的收获不是写出多少行代码，而是踩坑后的思考。外键约束删除失败让我第一次认真阅读了 MySQL 关于 FOREIGN_KEY_CHECKS 的文档；事务一致性问题让我理解了为什么 Spring 选择声明式事务而非编程式事务；JSP 与 JavaScript 的语法冲突让我明白了前后端分离的价值。

每一个 bug 都是一次学习机会。从 500 Internal Server Error 的茫然，到能根据堆栈信息定位到具体代码行，解决问题的效率在提升。我曾经花了两个多小时排查 request.getParameter() 返回 null 的问题，最后发现是 @MultipartConfig 注解没有加——这种经验在课本上是学不到的。

另一个深有感触的是：好的设计需要前瞻性。比如 DAO 层提供接受外部 Connection 的方法，最初觉得是过度设计，但当需要事务保护时发现这是必要的。如果一开始就为这种场景预留了接口，后期改动的代价就小得多。

九、展望

马上要做的事：

  1. 使用 Spring Boot + MyBatis 重构项目，用 AOP 管理事务、用注解替代 Servlet 配置
  2. 密码改为 BCrypt 加密存储
  3. 引入 Redis 缓存学生列表，减少数据库查询
  4. 补充 JUnit 单元测试覆盖核心 DAO 和 Service 方法

未来想尝试的方向：

  1. 用 Vue.js 重构前端，实现前后端分离
  2. 增加 WebSocket 实现多点名终端同步（教师屏点名，学生屏实时显示结果）
  3. 用 Docker 容器化部署（MySQL + Tomcat + 应用一键启动）
  4. 学习 Spring Security 实现 OAuth2 登录
